## 0. 执行摘要

| 级别 | 数量 | 影响 |
|---|---|---|
| **CRITICAL** | **7** | 阻断 v3.0.5.1 发布:构建失败、路由被绕过、ESLint 形同虚设 |
| **MAJOR** | **29** | 安全降级、错误吞没、测试盲区、可维护性差 |
| **MINOR** | **17** | 命名不一致、文档与代码漂移、清理类 |

**关键结论:**
1. **`src/components/v3/collab/index.ts` 引用了 3 个不存在的文件**(`MentionPicker`、`ChatRoom`、`CriticalEscalation`),其中 `MentionPicker`、`ChatRoom` 在 `messages/`,`CriticalEscalation` 在 `critical/`。如果某个 v3 报告页面真的 import 这个 barrel,会在 `vite build` 时编译失败,直接阻断 v3.0.5.1 发版。
2. **`server/` 目录 84 个 TS 文件中,只有 `server/index.ts` 被 `package.json` 的 `server` 脚本使用**。`fhir/`、`hl7/`、`dicom/`、`cdsHooks/`、`integration/`、`openapi/`、`search/`、`transcode/`、`routes/`、`middleware/`、`utils/` 全部 60+ 文件都是**孤儿代码**(`fhirRouter`、`hl7Router`、`dicomRouter`、`openapiRouter`、`reportRouter` 等 export 0 引用)。`server/routes/*` 引用了未安装的 `better-sqlite3` 运行时包。
3. **36 个前端文件加了 `// @ts-nocheck`**,几乎所有大页面都禁用了类型检查(包括 `ReportPage`、`WorklistPage`、`DicomViewerPage`、`NotificationCenter` 等),导致 tsconfig 里的 `strict: true`、`noUncheckedIndexedAccess: true` 在这些文件上**形同虚设**。`@ts-nocheck` 数量比实际 ts 错误还多,反而让 reviewer 失去信号。
4. **无 per-route ErrorBoundary**。`App.tsx` 只在最外层包了一个 `ErrorBoundary`,任何一个 lazy 页面抛错都会卸载整个 React 树,显示全屏兜底。`v3.0.5.1-A1` 之前已经描述过 122 个 lazy 路由、5 角色 RBAC 入口,缺少 page 级 ErrorBoundary 是产品级可用性缺陷。
5. **`AppLayout.tsx:18` 硬编码 `currentUser.role = '管理员'`**。所有登录用户进入界面后,侧边栏菜单、报表可见性、权限提示都按"管理员"渲染,与 `useAuth()` 解耦。`v3.0.5.1-A2-FLOW` 已经标了这条 CRIT,但同一个文件中还存在 `currentUser = { ...initialUsers[0], role: '管理员' as Role }`(行 18)— 此为代码层的 CRITICAL,不只是流程。
6. **存在 4 套并行 RBAC 实现**:`src/services/auth/rbacService.ts`(英文角色)、`src/types/index.ts`(`hasPermission(user, perm)`、中文角色)、`src/hooks/useAuth.ts`(硬编码 `pathPermissions` 白名单)、`backend/src/...`(NestJS Guards 但 0 引用)。修改任何一处权限语义都不会同步另外几处。
7. **`as any` 滥用 100+ 处**。最严重的是 `src/machines/reportMachine.ts:231-232`,`event as any` 出现在 XState v5 守卫里,意味着报告状态机 RBAC 边界已被绕过。
8. **重复 `sanitization.ts` / `validation.ts`**:`src/utils/sanitization.ts` 与 `src/security/sanitization.ts`、`src/utils/validation.ts` 与 `src/security/validation.ts` 互为相似但不同实现;`src/utils/currency.ts` 与 `src/utils/currencyFormat.ts` + `src/utils/decimal.ts` 都在做精度/格式化。

### CRIT-CODE-03  `as any` 大量使用,污染状态机 RBAC 边界

- **Severity:** CRITICAL
- **File:** `src/machines/reportMachine.ts:231-232`
- **Description:**
  ```ts
  rejectReasonRequired: ({ context, event }) => (event as any).reason?.trim().length > 0,
  qualityScoreSufficient: ({ context, event }) => ((event as any).qualityScore ?? context.qualityScore) >= 60,
  ```
  `ReportEvent` 联合类型在 `src/machines/reportMachine.ts:45-77` 已经定义,使用 `as any` 绕过 `ReportEvent` 联合类型,导致:
  - `reason` 字段只在 `{ type: 'REJECT'; reason: string }` 事件上存在,但守卫把它当作"所有事件都有" — 编译期不报错。
  - 任何 `PUBLISH` / `AMEND` / `CO_SIGN` 事件如果混入 `reason` 字段就能绕过校验。
- **Suggested fix:** 用 `XState v5` 的 discriminated narrow:
  ```ts
  rejectReasonRequired: ({ event }) => event.type === 'REJECT' && event.reason?.trim().length > 0,
  qualityScoreSufficient: ({ context, event }) => {
    const score = event.type === 'PUBLISH' || event.type === 'RE_EVALUATE' ? event.qualityScore : undefined
    return (score ?? context.qualityScore) >= 60
  },
  ```

### MAJOR-CODE-09  Zustand stores 异步无 try/catch,Promise rejection 直接进 Sentry

- **Severity:** MAJOR

  ```ts
        set({ exams: res.data as ExamDto[], loading: false })
      } else {
        set({ loading: false, error: res.error?.message ?? '加载失败' })
      }
    } catch (err) {
      set({ loading: false, error: err instanceof Error ? err.message : '网络错误' })
    }
  }
  ```
