## §1. Agfa Enterprise Imaging 概述

### 1.1 产品定位

Agfa HealthCare 的 **Enterprise Imaging (EI)** 是面向区域级/医院集团级的统一影像与临床内容管理平台。其核心定位并非单一 PACS,而是作为企业级 "Imaging Content Manager",在跨院区、跨模态、跨学科(放射、超声、心血管、病理、眼科、皮肤、内镜、临床摄影等) 的场景下,聚合影像与文档,统一调阅、存储、分发与生命周期管理。

在 G005 RIS 的对标体系中,Agfa EI 常被视为 "PACS + VNA + 影像协同 + AI 编排" 的复合体,即:

- **PACS 层**:影像归档与放射工作流(类似传统 PACS);
- **VNA 层**:以 DICOM 与非 DICOM 为中心的统一存储与去重;
- **业务编排层**:Ruboost(报告与业务自动化)与 AI Orchestrator(多厂商 AI 算法路由);
- **临床聚合层**:XERO 零足迹阅片、跨部门临床查看器、企业级权限与审计。

### 1.2 在 RIS 视角中的角色

对 RIS 系统而言,Agfa EI 的角色会随采购形态而变化:

| 形态 | EI 的角色 | RIS 的职责 |
|------|----------|------------|
| EI 作为主 PACS/VNA | 影像归档/调阅/分发主体 | 预约、检查登记、报告撰写、工作流编排、计费 |
| EI 作为区域 VNA | 多院区影像聚合与长期存储 | 与 EI 之间通过 IHE/XDS/IHE-RAD 交换 |
| EI 仅作科室级 PACS | 单一科室影像系统 | 与其它 PACS 并存,RIS 统一调度 |

本次调研以**形态一(单一院区 EI 主 PACS/VNA)** 为主线,同时兼顾形态二(集团部署)对 G005 RIS 提出的接口要求。

## §2. Enterprise Imaging 平台架构

### 2.1 逻辑分层

Agfa EI 在公开文档与白皮书中通常被描述为如下 5 个逻辑层次。G005 RIS 适配层主要与"集成层"对话,经"集成层"与下层交互。

```
┌─────────────────────────────────────────────────────────────┐
│ L5  临床消费层   XERO Viewer / Clinical Viewer / Mobile    │
├─────────────────────────────────────────────────────────────┤
│ L4  业务编排层   Ruboost (RUBAC) / Workflow Engine         │
├─────────────────────────────────────────────────────────────┤
│ L3  AI 编排层    AI Orchestrator / Algorithm Routing       │
├─────────────────────────────────────────────────────────────┤
│ L2  存储与归档层 VNA (DICOM Q/R, WORM, XDS, DICOMDIR)     │
├─────────────────────────────────────────────────────────────┤
│ L1  核心服务层   EI Core (Patient/Study/Order/Report)     │
└─────────────────────────────────────────────────────────────┘
              ▲              ▲              ▲
              │              │              │
        IHE-RAD/XDS    HL7 v2.x/ORM     DICOM/FHIR
              │              │              │
        ┌─────┴──────────────┴──────────────┴─────┐
        │         G005 RIS Adapter Layer          │
        └──────────────────────────────────────────┘
```

### 2.2 EI Core 服务层

EI Core 是 Agfa EI 平台的 "事实主数据服务",负责:

- **患者主索引 (Enterprise Patient ID)**:在 EI 域内维护患者 MPI,并通过 PIX/PDQ 向外暴露;
- **检查 / 序列 / 实例元数据**:以 DICOM 信息模型 (Patient→Study→Series→Instance) 为骨架,叠加 Agfa 私有信息对象 (Private Tags + DB 字段);
- **医嘱 (Order) 接收与状态机**:通过 HL7 v2 ORM/ORU、IHE RAD-1/RAD-2/RAD-3/RAD-4 等,与 RIS/Order Placer 集成;
- **报告 (Report) 主数据**:以 Ruboost 为报告写作与流转载体,Core 维护报告的版本、签名、修订链;
- **权限与审计**:RBAC、Break-the-Glass、审计日志,统一接入 SSO(支持 SAML 2.0、OpenID Connect)。

> 对 G005 RIS 的含义:RIS 不应直接操作 DICOM 对象,而应通过 EI Core 的"业务 API"完成"谁的患者/什么检查/什么状态/报告进展如何"的查询与变更。

### 2.3 Ruboost (报告与业务编排层)

Ruboost 在 Agfa 内部常缩写为 **RUBAC**,是 EI 之上的"业务中台"模块。它把传统报告工作台 (Reporting Workstation) 与企业级流程引擎合并:

- **报告模板与结构化字段**:按模态/专科维护可配置模板,字段可来自 DICOM SR TID、AI 输出、自定义数据源;
- **多阶段签字**:住院医师→主治医师→主任医师→终审,可与电子签名 (PKI / 数字证书) 集成;
- **危急值 (Critical Findings) 通知**:在 Ruboost 内闭环,与 RIS 的危急值通知流程需要严格对齐;
- **跨部门订阅**:放射报告可被临床科室订阅,临床文档可被放射参考;
- **BI / 报表**:Ruboost 内置 BI,可输出 SLAs、报告周转时间 (TAT)、亚专科工作量等。

### 2.4 AI Orchestrator

AI Orchestrator 是 Agfa 应对"多厂商 AI 算法孤岛"问题的统一编排层。它在 EI 内部署:

- **算法路由 (Algorithm Routing)**:根据检查类型、部位、协议,把 DICOM 实例路由到不同厂商的 AI 服务(如肺结节 CAD、骨折检测、脑出血分诊、冠脉 CTA);
- **结果回写**:AI 输出 (DICOM SR / DICOM SEG / DICOM-RT / 自定义 JSON) 写回 EI,可被报告模板直接引用;
- **结果订阅**:RIS 可订阅 AI 完成事件,从而触发"AI 预读→医生确认"工作流;
- **沙箱与计费**:为每个 AI 厂商维护独立计费、配额与回放沙箱。

### 2.5 VNA (Vendor Neutral Archive)

VNA 是 EI 的存储与归档核心:

- **格式中立**:DICOM 为主,但允许以 PDF、JPEG、TIFF、MP4、原生病理 (WSI / DICOM Pathology)、心电图 (HL7 aECG) 等归档;
- **生命周期 (ILM)**:在线、近线、归档、销毁四级,可与冷存储 (AWS S3/Glacier、Azure Blob Archive、本地磁带库) 联动;
- **IHE XDS/XDS-I.b**:对外作为文档注册中心 (Registry) 与文档仓库 (Repository),可被医院 EHR、CDR 通过 XDS 拉取;
- **DICOM Q/R (C-MOVE/C-GET) 与 WADO-URI/WADO-RS**:对外提供调阅;
- **去重与压缩**:以 Study UID + SOP Instance UID + Hash 进行实例级去重,支持无损/有损压缩策略。

### 2.6 与外部系统的接口矩阵

| 外部系统 | EI 暴露接口 | G005 RIS 期望对接的接口 | 备注 |
|----------|------------|-----------------------|------|
| HIS / RIS | HL7 v2.x ORM/ORU/ADT、IHE RAD | HL7 v2.x ORM/ORU、IHE RAD-1/2/3/4/12/13 | G005 RIS v3.0.6.1 已实现 ORM/ORU/ADT,RAD 套件部分实现 |
| EHR / EMR | IHE XDS.b / XDS-I.b / FHIR R4 (ImagingStudy、ImagingMedia、DiagnosticReport) | FHIR R4 ImagingStudy/DiagnosticReport | G005 RIS 需扩展 FHIR 资源适配 |
| AI 厂商 | 内部 API + DICOM router | 通过 EI 间接使用 | 不需 RIS 直连 |
| 患者门户 | FHIR / 私有 REST | 间接调阅 | 不在 RIS 范围 |
| 区域影像 / 集团 VNA | XCA / XCA-I / DICOM Q/R | 通过 EI 中转 | 由 EI 负责 |
| 计费/医保 | HL7 v2.x BAR/PAS、自定义 | HL7 v2.x BAR/PFT | 由 HIS/RIS 主导,EI 不参与 |

## §3. 调研要点

本章按 Agfa EI 四个核心子系统,逐一拆解对 G005 RIS 的调研要点。

### 3.1 EI Core

#### 3.1.1 调研目标

确认 EI Core 在以下业务边界上的"权威性"与"可委托性":

- 患者身份 (Patient Identity);
- 检查状态 (Scheduled → In Progress → Completed → Verified);
- 报告状态 (Preliminary → Final → Amended → Corrected);
- 危急值状态 (Critical Result Notification)。

#### 3.1.2 关键问题清单

1. **Patient ID 主权威**:EI Core 是否接管患者 MPI?若由 HIS/RIS 主权威,EI Core 是否支持 "Assigned Authority" 信任链?
2. **Order 来源**:EI Core 是否要求所有检查都必须由 Order Placer(RIS/HIS)以 ORM 下发?是否支持"在 EI 内手动开单"?
3. **Study UID 生成策略**:由 EI Core 还是 RIS 生成?冲突时如何仲裁?
4. **状态机对外暴露**:EI Core 是否对外提供 REST/FHIR 查询"某 Order 当前状态"的接口?G005 RIS 可否通过订阅代替轮询?
5. **报告修订 (Amended/Corrected Report) 的语义**:是否符合 IHE Revise Reporting Profile?

#### 3.1.3 对 G005 RIS 的潜在影响

- 若 EI Core 接管 Patient MPI,RIS 需切换为 "Assigned Authority" 模式,即不再自己生成 PID,而是接受 EI Core 分配的 PID,并在所有下游消息中透传;
- 若 EI Core 接管 Study UID,RIS 应停止生成 DICOM Study UID,改为在 ORM 中携带 EI 生成的 Accession Number,EI 反向回填 UID 至 RIS;
- RIS 的"检查状态机"需要与 EI 状态机做字段级映射;出现状态漂移时需要定义"以 EI 为准"或"以 RIS 为准"的仲裁规则。

### 3.2 RUBAC 报告

#### 3.2.1 调研目标

RUBAC(Ruboost)是 EI 的报告与业务编排模块。G005 RIS 当前已有自研报告工作台,需调研:

- 报告写作工具是放在 RIS 还是迁到 RUBAC?
- 报告签名 (电子签名 + CA 证书) 由哪一方负责?
- 危急值通知是否在 RUBAC 闭环?

#### 3.2.2 关键问题清单

1. **报告主权威**:RUBAC 是否要求"所有放射报告必须在 Ruboost 内撰写"?是否允许 RIS 撰写后通过 ORU^R01 回写?
2. **结构化报告**:RUBAC 是否支持 TID 1500 / TID 2000 (Chest / Heart) 等 IHE 模板?是否允许扩展自定义 TID?
3. **报告版本链**:Amended/Corrected/Addended 三种修订模式,RUBAC 如何区分?是否与 IHE Revise Reporting 一致?
4. **危急值通知**:RUBAC 是否提供危急值通知接口 (FHIR Task / Communication / 自定义)?超时未确认是否回写 RIS?
5. **绩效/BI 数据**:RUBAC 是否对外暴露报告 TAT、工作量、亚专科产能等 BI 数据?RIS 是否需要订阅?

#### 3.2.3 对 G005 RIS 的潜在影响

- **路线 A**:报告主权威留在 RIS,RUBAC 通过 ORU^R01 接收"G005 RIS 已签报告",仅做归档与分发。G005 RIS 工作量小,但失去 AI 协同与结构化模板优势。
- **路线 B**:报告主权威迁至 RUBAC,RIS 仅负责检查登记与工作流编排。RIS 需新增"报告状态订阅/拉取"接口,且 RUBAC 模板需要 RIS 参与联合建模。
- **路线 C(折中)**:按模态分治 —— 放射、超声、病理使用 RUBAC 报告;内镜、临床摄影仍由 RIS 报告工作台承接。

### 3.3 AI Orchestrator

#### 3.3.1 调研目标

G005 RIS 当前未直接集成 AI 编排,AI 集成通常由 PACS 或独立 AI 平台承担。本次调研需要回答:

- AI Orchestrator 是否对 RIS 透明?
- RIS 是否需要感知 AI 完成事件?
- AI 计费与配额是否需 RIS 配合?

#### 3.3.2 关键问题清单

1. **AI 完成事件**:Orchestrator 是否对外提供 HL7 v2.x 触发消息 / FHIR DiagnosticReport.derivedFrom 关联 / 自定义 Webhook?
2. **AI 输出溯源**:AI 结果与原始 Study 的关联是否持久化?是否可在 RIS 工作站点击"查看 AI 推断"?
3. **AI 与危急值**:AI 触发的"疑似脑出血""主动脉夹层"等是否自动升级为危急值,是否回灌 RIS?
4. **多厂商并存**:Orchestrator 是否允许"肺结节用 A 厂商、骨折用 B 厂商"?路由策略由谁配置?
5. **结果回写字段**:AI 输出是写 DICOM SR、还是 SR + 私有 Tag、还是 JSON Sidecar?RIS 报告模板如何引用?

#### 3.3.3 对 G005 RIS 的潜在影响

- 若 AI Orchestrator 触发"危急值预升",RIS 需新增"AI-Preliminary Critical"状态,并与原有危急值流程并行;
- 报告模板若要"AI 预填 + 医生确认",RIS 需具备拉取 AI 派生字段(结节尺寸、骨折分型、CAD-RADS 等级等)的能力;
- RIS 不必直连 AI 厂商,但需在检查预约/医嘱阶段携带 AI 申请标志(必要时),以便 Orchestrator 路由。

### 3.4 VNA

#### 3.4.1 调研目标

VNA 在 EI 体系内是影像的"长期归档主权威"。调研重点:

- VNA 是否对外暴露 DICOM Q/R、WADO-URI、WADO-RS、IHE XDS-I.b?
- VNA 的生命周期策略是否影响 RIS 留存策略?
- VNA 是否支持"以非 DICOM 形态归档" (PDF、WSI、aECG、PDF/A)?

#### 3.4.2 关键问题清单

1. **DICOM Q/R**:VNA 作为 Q/R Provider 时,C-FIND 字段是否完整支持?特别是 Scheduled Procedure Step (PPS) 与 Performed Procedure Step 是否能正确返回?
2. **WADO**:WADO-URI 与 WADO-RS 的部署形态?是否要求 DICOMweb over TLS?token 如何签发?
3. **XDS-I.b**:VNA 是否同时充当 XDS-I.b Document Registry / Repository?是否要求 Affinity Domain 配置?
4. **非 DICOM**:病理 WSI、内镜视频、心电图、临床 PDF 等是否同样归档在 VNA?以何种 SOP Class 注册?
5. **数据迁移**:若历史数据从老 PACS 迁入 VNA,RIS 是否需要重新打 Accession Number 与 Study UID 映射?

#### 3.4.3 对 G005 RIS 的潜在影响

- RIS 的"调阅链接"生成器需要升级,支持 WADO-URI/WADO-RS + DICOMweb,而不是简单拼接老式 PACS URL;
- 跨院区调阅 (XCA / XCA-I) 不需要 RIS 直连,由 EI 之间完成,但 RIS 工作站需要在 UI 层选择"本院 / 集团";
- 非 DICOM 归档会让 RIS 的"附件管理"概念扩大,需新增"非影像内容归档"条目;
- 数据迁移期间,RIS 应冻结 Accession Number 分配,改为由 VNA 主导的映射回灌,事后一次性校正。

### 4.3 与国家级/区域互联互通评级要求的对位

中国医院信息互联互通标准化成熟度测评(四级甲、五级乙、五级甲)与电子病历应用水平分级评价(6 级、7 级、8 级)对 PACS/VNA 提出过如下要求:

- 五级乙:要求影像可通过 IHE XDS-I.b 在院内跨域调阅;
- 五级甲:要求与区域影像平台通过 XCA-I 互联;
- 电子病历 7 级:要求结构化放射报告、影像所见/结论可被 EMR 引用;
- 电子病历 8 级:要求 AI 辅助诊断结果可在 EMR 呈现,危急值闭环管理。

Agfa EI 在以上几点上有相对成熟的方案;G005 RIS 若采用 Agfa EI 作为主 PACS,需要 RIS 侧补齐 XDS.b Consumer、FHIR ImagingStudy 资源、危急值闭环等能力。

### 5.1 集成切入点候选清单

### 5.2 推荐集成形态

考虑 G005 RIS 的历史包袱与产品定位,**推荐分三阶段演进**:

- **阶段 A(适配)**:维持 v3.0.6.1 既有 HL7 v2.x 主干,新增 I4 (PPS/Storage Commitment)、I7 (FHIR DiagnosticReport) 作为 Agfa EI 适配层。零侵入,可在 v3.0.7 一次小迭代内完成。
- **阶段 B(协同)**:引入 I5 (XDS.b)、I9 (DICOMweb)、I10 (危急值)、I11 (AI 事件)。需要 G005 RIS 增设"影像协同服务"子系统,工作量较大,建议放在 v3.0.8/v3.0.9。
- **阶段 C(融合)**:I13 (报告结构化字段对齐)、I6 (FHIR ImagingStudy)、I8 (FHIR Subscription) 全面铺开。属于产品级重构,需要单独的产品线投入。

### 5.3 与 AI Orchestrator 的协同设想

研究文档允许提出"设想",但应明确标记为设想,不应承诺落地:

1. RIS 在 ORM 中携带 `AI-Request` 标志与 `AI-Vendor` 偏好(可选),EI 接收后透传至 AI Orchestrator;
2. AI Orchestrator 完成推理后,通过 FHIR `DiagnosticReport.note` 或私有 Segment,把 AI 派生字段推送回 RIS;
3. RIS 在报告工作台 UI 中,把 AI 派生字段作为"待确认草稿"展示,由医生勾选/修正;
4. 危急值 AI 自动升级时,RIS 通过 FHIR `Task` 接收"AI-Critical"任务,与既有危急值流程并行不冲突;
5. RIS 不直连 AI 厂商,所有计费、配额、回放均由 AI Orchestrator 统一处理。

3. Ruboost 模板是否允许客户自定义 TID,直接影响阶段 C 的"报告字段对齐"工作量;
4. 集团部署 (XCA-I) 是否纳入范围,会显著拉长阶段 B 的联调时间。

## §8. 风险评估

### 8.1 技术风险

| 编号 | 风险 | 等级 | 描述 | 缓解策略 |
|------|------|------|------|----------|
| T1 | EI 版本碎片化 | 高 | 不同客户 EI 版本不一,RIS 适配层需多版本兼容 | 在适配层抽象 "EI Profile" 概念,按客户现场版本加载 |
| T2 | 接口签名漂移 | 中 | EI 升级可能改变私有 API / HL7 Z 段 | 关键字段优先用 IHE 标准,避免依赖私有段 |
| T3 | 状态机冲突 | 中 | RIS 与 EI 状态机漂移 | 定义"以 EI 为准"或"以 RIS 为准"的仲裁规则,定期对账 |
| T4 | FHIR 资源成熟度 | 中 | ImagingStudy / ImagingMedia 在 R4 中仍处于 trial-use | 关注 R4B/R5 演进,关键路径使用 DICOMweb |
| T5 | AI 事件流可靠性 | 中 | AI 事件可能丢失、延迟、重复 | 引入去重 + 重放 + 业务幂等设计 |
| T6 | 大体量影像调阅性能 | 中 | WADO-RS 在低带宽下体验差 | 启用 DICOM 转码(降采样、jpeg-lossy)、前端按需分块 |
| T7 | 数据迁移一致性 | 高 | 历史 PACS 数据迁入 VNA 后,Accession Number / Study UID 需重新映射 | 冻结号段、双写期、回灌校验 |
