## §1 Carestream Vue 概述

### 1.1 公司背景

Carestream Health(以下简称 Carestream)是一家总部位于美国纽约州罗切斯特的医疗成像与医疗 IT 解决方案提供商,前身为伊士曼柯达公司医疗成像部门,2007 年被 Onex Corporation 收购后独立运营。公司在全球医疗影像信息化领域拥有超过 100 年的技术积累,产品线覆盖 CR/DR 设备、牙科成像、兽用成像以及医院/区域级 PACS/RIS/HIS 集成方案。截至 2024 年,Carestream 在全球 150 多个国家拥有装机用户,服务于超过 13,000 家医疗机构。

在中国市场,Carestream 主要通过其本土合作伙伴(锐珂(上海)医疗器材有限公司)开展业务,客户群以三级医院、专科影像中心以及医联体为主。其 RIS/PACS 产品在放射科、超声科、病理科、内镜中心均有应用案例。

### 1.2 Vue 产品线定位

Carestream 当前主推的"PACS"实际上并非单一软件产品,而是以 **Vue Cloud** 为底座、以 **Vue PACS** 为核心工作站的系列解决方案。Vue 系列的官方定位是 **Clinical Collaboration Platform(临床协作平台)**,目标是打破传统放射科与临床科室之间的信息孤岛,支持影像数据在全院乃至区域内的流转与共享。

从产品矩阵来看,Vue 系列主要包含以下组件:

- **Vue PACS**:核心影像归档与诊断工作站,提供 DICOM 影像的接收、存储、调阅、标注、报告撰写、关键影像标记(KP)、关键对象标记(KO)等功能。
- **Vue Motion**:零足迹(Zero-Footprint)影像浏览器,支持多终端(PC、平板、手机)通过 HTML5 浏览器直接访问影像,无需安装客户端。
- **Vue Cloud**:基于云的弹性存储与计算平台,支持混合云(Hybrid Cloud)部署,提供影像长期归档、灾备、AI 推理算力调度等能力。
- **Vue Reporting**:结构化报告平台,支持放射科报告模板、语音识别集成、危急值通报。
- **Vue Archive**:独立的企业级影像归档(VNA, Vendor Neutral Archive),遵循 IHE XDS-I.b 规范。
- **Vue Connect**:院内、院间、区域级影像共享网关,支持 IHE XDS Registry/Repository 模式。
- **Vue eHealth**:患者影像门户,支持患者通过浏览器/小程序查阅本人影像与报告(对应本文 §3.3 Patient Engagement)。

### 1.3 与 G005 RIS 的潜在关系

G005 RIS 是面向中小型放射科、超声科、影像中心的轻量级 RIS 系统,当前 v3.0.6.1 主要聚焦于检查预约、登记、计费、报告流转、DICOM Worklist 提供等核心 RIS 流程。G005 RIS 在 v3.0.0 起即提供了对主流 PACS 的 DICOM 标准接口对接能力(DICOM C-STORE SCP、Modality Worklist SCP、MPPS SCU),但尚未与任何商业 PACS 厂商进行过深度业务级集成。

调研 Carestream Vue 的核心目的,是评估未来 v3.0.7+ 是否需要、是否值得与 Vue PACS 进行以下三类集成:

1. **数据流集成**:RIS 检查单、检查状态、报告回写 PACS。
2. **工作流集成**:基于 IHE 集成规范(SWF、PIR、ARI)的跨系统工作流编排。
3. **业务级集成**:报告互通、患者主索引(EMPI)同步、AI 推理结果回灌。

## §2 Vue PACS / Vue Motion 架构

### 2.1 整体架构视图

Carestream Vue 采用分层架构,自下而上大致分为四层:

1. **基础设施层**:物理服务器 / 虚拟机 / 公有云 / 私有云,可由客户自建或由 Carestream 提供的 Vue Cloud 托管。
2. **数据持久层**:DICOM 影像存储(短期在线 / 长期归档)、关系型数据库(Oracle/SQL Server/PostgreSQL)、对象存储(S3 兼容)。
3. **服务层**:DICOM 服务(Q/R、C-STORE、MWL、MPPS、Storage Commitment)、IHE 集成引擎、HL7 v2.x 接口引擎、RESTful API 网关、AI 推理编排。
4. **表现层**:Vue PACS 诊断工作站(Windows 原生)、Vue Motion Web 浏览器、Vue eHealth 患者门户、移动端 App。

### 2.2 Vue PACS 核心组件

根据公开资料,Vue PACS 工作站通常包含以下核心模块:

- **诊断阅片模块(Viewing)**:支持多序列同步滚动、MPR/MIP/3D 重建、影像融合、CAD 标注叠加、关键影像标记(KP)、关键对象标记(KO)、DICOM-SR 渲染。
- **报告撰写模块(Reporting)**:与 Vue Reporting 联动,支持结构化模板、语音听写(集成 Nuance Dragon Medical / M*Modal)、危急值自动通知、报告双签、报告修订痕迹保留。
- **工作流编排模块(Workflow)**:支持放射技师、住院医师、主治医师、审核医师的多级流转,集成 IHE Scheduled Workflow(SWF)与 Post-Processing Workflow 规范。
- **影像后处理模块(Advanced Visualization)**:3D 容积重建、心脏钙化评分、结肠虚拟内镜、乳腺影像 CAD、肺结节 CAD 等高级可视化算法,部分功能依赖 GPU 加速。
- **教学与科研模块(Education/Research)**:支持 DICOM 匿名化导出、研究数据库构建、AI 模型训练样本管理。

Vue PACS 客户端历史版本依赖 Windows 桌面环境(.NET WPF / WinForms),自 Vue 12.x 起开始引入 Web 化客户端,但完整的诊断级功能(尤其是 3D 后处理)仍以桌面客户端为主,Web 客户端定位于"轻量级阅片 + 跨院调阅"。

### 2.3 Vue Motion 架构

Vue Motion 是 Carestream 应对移动医疗、跨院协同、远程会诊需求推出的 Zero-Footprint 解决方案。其技术特点:

- **纯 HTML5 + JavaScript**:基于 HTML5 Canvas / WebGL 渲染 DICOM 影像,无需 ActiveX、无需本地客户端安装。
- **服务端影像转码**:原始 DICOM 影像在服务端被转码为 JPEG2000 / H.265 / WebP 等流式格式,通过 HTTP/HTTPS 协议分块下发到浏览器。
- **DICOMweb 协议**:Vue Motion 对外暴露 WADO-RS、QIDO-RS、STOW-RS 接口,符合 DICOM 标准第 18 章定义的 Web 访问规范。
- **多终端适配**:支持响应式布局,可在 iPad、Android 平板、Windows 笔记本、Surface Pro 等设备上保持一致的阅片体验。
- **多用户并发**:服务端采用连接池 + 流控策略,支持数十名临床医师同时在线阅片而不显著降低性能。

Vue Motion 的典型应用场景包括:

- 急诊科医师在值班手机上查阅 CT 影像;
- 临床科室医师在病房/门诊工作站调阅患者历史影像;
- 医联体内下级医院向上级医院发起远程会诊申请;
- 患者通过 Vue eHealth 在家用手机查阅本人影像。

### 2.4 集成接口能力

从 G005 RIS 集成的角度,Vue 系列对外暴露的接口能力可大致归为以下几类:

| 接口类型 | 协议 | 说明 |
|---|---|---|
| DICOM | C-STORE SCP/SCU | 影像接收/发送 |
| DICOM | C-FIND SCP/SCU | 患者/检查/序列查询 |
| DICOM | C-MOVE SCP/SCU | 影像拉取/转发 |
| DICOM | Modality Worklist | 检查预约下发到设备 |
| DICOM | MPPS | 检查执行状态回传 |
| DICOM | Storage Commitment | 影像归档确认 |
| HL7 v2.x | ADT^A01/A04/A08 | 患者基本信息同步 |
| HL7 v2.x | ORM^O01 | 检查申请 |
| HL7 v2.x | ORU^R01 | 报告结果回传 |
| HL7 v2.x | MDM^T02 | 文档型报告 |
| IHE | XDS-I.b | 跨院影像共享 |
| IHE | PIX / PDQ | 患者主索引查询 |
| IHE | SWF / PIR | 放射工作流编排 |
| RESTful | DICOMweb | Web 端影像访问 |
| RESTful | 私有 API | Vue Reporting、AI Workflow |

需要强调的是,以上接口能力来源于公开规范和行业经验,具体到 Carestream Vue 的真实实现细节(接口地址、字段映射、消息样例、版本兼容矩阵),本文档**不予确认**。实际集成时必须以 Carestream 官方提供的《Vue Integration Specification》为准。

## §3 调研要点

本节是本文档的核心部分,围绕四个调研主题展开,每个主题包含:调研目标、关键问题、初步发现、待澄清事项。

### 3.1 Vue PACS 核心

#### 3.1.1 调研目标

评估 G005 RIS 与 Vue PACS 在 DICOM 与 HL7 双通道上的互通能力,识别在检查预约、检查状态同步、报告回写三个核心场景下可能需要的接口扩展或工作流改造。

#### 3.1.2 关键问题

- G005 RIS 当前通过 DICOM Modality Worklist 下发到 CR/DR/CT/MR 设备的工作流,是否需要针对 Carestream 设备(尤其是 Carestream 制造的 CR/DR)做特殊字段映射?
- Vue PACS 作为 DICOM C-STORE SCP 接收来自 Carestream 模态设备的影像,G005 RIS 是否需要承担"中转检查"角色(即 RIS → PACS → 设备 → PACS → RIS 的双向同步)?
- Vue PACS 的报告回写通道(HL7 ORU^R01)对报告状态字段(初步/最终/修订/取消)的支持程度,是否与 G005 RIS 的报告状态机完全兼容?
- Vue PACS 是否支持 DICOM SR(结构化报告)作为报告传输载体?G005 RIS 当前主要输出 PDF 报告,是否需要升级为 DICOM SR?

#### 3.1.3 初步发现

- 公开资料显示,Vue PACS 完全遵循 DICOM 3.0 标准与 IHE 放射技术框架(Radiology Technical Framework),在标准协议层面与 G005 RIS 当前实现的能力是兼容的。
- Vue Reporting 支持 HL7 v2.5 ORU^R01 消息,字段映射在 Carestream 官方文档中有详细说明,包括 OBR-25(报告状态)、OBX-5(报告内容)、OBX-11(观察结果状态)。
- Vue PACS 对 DICOM SR 的支持在 12.x 版本后趋于成熟,但传统医院仍以 HL7 ORU 为主,G005 RIS 短期内不需要为了对接 Vue 而强行升级到 DICOM SR。

#### 3.1.4 待澄清事项

- G005 RIS 当前 v3.0.6.1 默认启用的 DICOM 上行端口、AE Title、传输语法与 Carestream Vue 的默认配置是否冲突,需要现场实测。
- Carestream 自家模态设备(DRX-Revolution、DRX-Eve 等)是否存在私有 DICOM Tag(Private Tag)需要解析,这部分信息不在公开文档中。
- Vue PACS 在中国本地化部署时是否需要单独的"国密"模块支持,需要与锐珂医疗确认。

### 3.2 Clinical Collaboration Platform

#### 3.2.1 调研目标

Carestream 将 Vue 系列定位为"Clinical Collaboration Platform",意在打破放射科与临床科室的壁垒。本调研主题关注:G005 RIS 作为放射科 RIS,在这一"打破壁垒"愿景中应扮演什么角色?能否从单纯的"放射科内部系统"演变为"影像驱动的临床协同平台"?

#### 3.2.2 关键问题

- G005 RIS 是否需要扩展支持非放射科室(超声、心电、病理、内镜、口腔)的检查预约?这涉及数据模型的大幅改造。
- G005 RIS 是否需要提供开放 API(Open API),允许临床科室的 EMR / 移动护理系统直接调用 RIS 的检查预约、状态查询、报告调阅能力?
- 跨院影像共享(XDS-I.b)对 G005 RIS 的数据模型有何影响?G005 RIS 是否需要支持"机构(Institution)"、"文档库(Document Repository)"等 XDS 概念?

#### 3.2.3 初步发现

- G005 RIS 当前定位明确为"放射 RIS",短期内不打算扩展为"多科室综合 RIS",但需要在 API 层留出扩展空间。
- G005 RIS 在 v3.0.5 已引入 OpenAPI 3.0 规范,具备一定的开放能力,但功能范围仅覆盖检查预约、报告调阅,未覆盖工作流编排。
- 跨院影像共享属于医联体/区域平台范畴,G005 RIS 在 v3.0.6.1 不做此方向投入,只确保 DICOM 协议层面的基础互通。

#### 3.2.4 待澄清事项

- "Clinical Collaboration Platform"在 Carestream 的官方定义中是否包含"对 RIS 厂商开放 API"的承诺?这决定了 G005 RIS 在该平台中的角色定位是"集成方"还是"被集成方"。
- G005 RIS 是否需要支持 HL7 FHIR?这与 G005 RIS 当前 HL7 v2.x 为主的接口策略存在代际差异。

### 3.3 Patient Engagement

#### 3.3.1 调研目标

Vue eHealth 是 Carestream 的患者影像门户,支持患者通过 Web/App 查阅本人影像与报告。本调研主题关注:G005 RIS 是否需要构建类似的患者门户?如果不需要直接对患者开放,G005 RIS 的报告数据如何通过 Carestream 平台(或第三方平台)触达患者?

#### 3.3.2 关键问题

- 中国《医疗机构病历管理规定》《电子病历应用管理规范》对患者影像调阅的合规要求是什么?G005 RIS 是否需要支持实名认证、电子签名、访问审计?
- G005 RIS 是否需要支持报告的"患者友好版"(Patient-Friendly Report)?即把放射科专业术语翻译为通俗语言?
- 患者影像分享(Share My Images)在中国法规下的可行性?是否需要对接微信小程序/支付宝小程序?

#### 3.3.3 初步发现

- 中国法规允许患者本人或授权委托人查阅与复制客观病历资料,包括影像与报告。
- G005 RIS 当前未提供患者门户,但 v3.0.5 已提供标准的 RESTful 报告调阅 API,理论上第三方患者门户可通过 API 集成。
- 国内医院普遍将患者影像/报告查询功能统一在"医院公众号"或"互联网医院 App"中,G005 RIS 不需要独立建设患者门户。

#### 3.3.4 待澄清事项

- Vue eHealth 是否在中国本地化部署中得到完整支持?锐珂医疗是否提供中文患者门户?
- G005 RIS 的报告 PDF 字体在移动端浏览器中的渲染兼容性,可能影响患者体验。

### 3.4 AI Workflow

#### 3.4.1 调研目标

AI 是当前医学影像行业的核心议题。Carestream Vue 提供了 AI Workflow 编排能力,支持第三方 AI 算法(如肺结节、乳腺、脑出血、骨折 CAD)以"插件"形式集成。本调研主题关注:G005 RIS 在 AI 浪潮中应该扮演什么角色?是否需要支持 AI 推理触发、AI 结果回灌、AI 报告字段填充?

#### 3.4.2 关键问题

- G005 RIS 是否需要支持 DICOM SR TID 1500(Imaging Measurement Report)作为 AI 结果传输载体?
- AI 推理通常由 PACS 触发(影像入库即触发),G005 RIS 是否需要在检查申请阶段就声明"该检查需要 AI 辅助"?
- AI 结果(标注、热图、结构化测量值)如何回写到 RIS 报告?是作为独立字段,还是嵌入到报告正文?

#### 3.4.3 初步发现

- 主流 AI 厂商(推想、联影智能、数坤、依图、腾讯觅影)目前主要与 PACS 厂商集成,G005 RIS 作为 RIS 通常不被 AI 厂商直接对接。
- AI 结果回灌 RIS 报告目前不是行业主流,大部分医院的 AI 结果是 PACS 端医师查看,报告正文仍由放射医师手写。
- G005 RIS v3.0.6.1 的报告模型已经支持"结构化字段"(Structured Field),未来可承载 AI 结构化结果。

#### 3.4.4 待澄清事项

- Carestream 自有的 AI 算法(如 Lung Nodule CAD、Mammography CAD)是否在中国监管机构(NMPA)取得注册证?这关系到能否在中国医院合法使用。
- 国家卫健委、国家药监局对"AI 辅助诊断"的合规要求,需要法务与合规团队介入。

## §4 行业对标

### 4.1 对标对象

为客观评估与 Carestream Vue 集成的价值与成本,我们将 G005 RIS 现状与同类 RIS 产品(国内、外)在 PACS 集成深度、AI 集成、患者门户、开放 API 四个维度进行对标。

对标对象包括:

- **国内综合 PACS/RIS 一体化厂商**:东软、卫宁健康、创业慧康、嘉和美康(以 HIS/EMR 为主)、海泰、岱嘉(图文报告系统);
- **国内专业 PACS 厂商**:锐珂(本土化 Vue)、巨鲨、飞图、汇利斯通、华海医信;
- **国际 PACS 厂商**:Carestream Vue、GE Centricity PACS、Philips IntelliSpace PACS、Siemens syngo.plaza、Fujifilm Synapse PACS、Agfa Enterprise Imaging;
- **新兴云原生 PACS**:Ambra Health、Nucleus Health、Life Image、PaxeraHealth。

### 4.2 对标维度

| 维度 | G005 RIS 现状 | 国际厂商平均水平 | 差距评估 |
|---|---|---|---|
| DICOM 标准支持 | 完整支持 C-STORE/MWL/MPPS/Q-R | 完整支持 | 持平 |
| HL7 v2.x 支持 | 完整支持 ADT/ORM/ORU/MDM | 完整支持 | 持平 |
| IHE 集成规范 | 部分支持(SWF、PIR) | 完整支持(XDS、ATNA、BPPC) | 落后 |
| AI 集成 | 未支持 | 普遍支持(插件式) | 落后 |
| 患者门户 | 未支持(提供 API) | 大多支持 | 落后 |
| 移动端阅片 | 未支持(仅报告) | 普遍支持 | 落后 |
| 开放 API | OpenAPI 3.0(部分) | 完整 RESTful + FHIR | 落后 |
| 云原生架构 | 否(传统部署) | 部分支持(混合云) | 落后 |
| 多语言 | 中文、英文 | 多语言 | 持平 |
| 本土化合规 | 等保三级、HIPAA 未做 | HIPAA、GDPR、NMPA | 部分落后 |

### 4.3 对标结论

从对标结果看,G005 RIS 在**标准协议(DICOM、HL7 v2.x)**层面与国际厂商基本持平,这是 G005 RIS 的传统优势区——协议兼容、部署轻量、上手简单。但在**IHE 集成规范深度、AI 集成、移动端、患者门户、云原生**等新兴维度上,G005 RIS 处于追赶位置。

这一现状决定了 G005 RIS 与国际 PACS 厂商(包括 Carestream Vue)的集成策略应该是:

1. **在已有优势区(标准协议)做深做透**:DICOM 与 HL7 的字段映射、消息可靠性、性能调优;
2. **在新兴维度保持克制**:AI、移动端、患者门户不与 PACS 厂商正面竞争,而是通过开放 API 配合 PACS 厂商的协同能力;
3. **在 IHE 规范上补课**:XDS、PIX/PDQ、ATNA 是大型医院与区域平台的硬性要求,G005 RIS 必须在 v3.0.7+ 启动 IHE 合规性认证。

## §5 潜在集成

### 5.1 集成场景设想

基于 §3、§4 的调研,初步设想 G005 RIS 与 Carestream Vue 在以下五个场景中存在集成可能:

#### 场景 1:标准 DICOM/HL7 互通(基线场景)

- G005 RIS 作为 Modality Worklist Provider,通过 DICOM MWL 向 Carestream 自家模态设备下发检查列表;
- Carestream Vue PACS 作为 C-STORE SCP 接收设备上传的影像;
- 报告由 Vue Reporting 撰写后,通过 HL7 ORU^R01 回传到 G005 RIS;
- G005 RIS 将报告状态同步给 HIS/EMR。

**集成度评估**:低(纯标准协议,无需定制开发)。

#### 场景 2:IHE XDS 区域影像共享

- 在医联体/区域平台中,G005 RIS 作为 Document Source,Vue Archive 作为 Document Repository;
- 跨院调阅通过 XDS Registry 实现;
- G005 RIS 需要实现 XDS-I.b Provide & Register Transaction。

**集成度评估**:中(需要新增 XDS 适配器,但 Carestream Vue 已原生支持)。

#### 场景 3:Vue Motion 跨终端报告调阅

- G005 RIS 的报告 PDF/HTML 通过 DICOMweb 协议推送到 Vue Motion;
- 临床医师通过浏览器调阅患者历史报告时,可同时查看相关影像;
- G005 RIS 不需要为 Vue Motion 单独开发,只需确保 OpenAPI 输出可被 Vue Motion 消费。

**集成度评估**:低-中(需要 G005 RIS 提供符合 DICOMweb 的 Web 访问端点)。

#### 场景 4:AI 推理结果回灌

- Carestream Vue 内部的 AI 引擎(肺结节 CAD、乳腺 CAD)生成的结构化结果;
- 通过 DICOM SR 或私有 API 推送到 G005 RIS;
- G005 RIS 将 AI 结果填充到报告的"AI 辅助诊断意见"字段;
- 放射医师在审核报告时可见 AI 提示。

**集成度评估**:高(需要 G005 RIS 报告模型支持 AI 字段,涉及工作流改造)。

#### 场景 5:患者门户报告共享

- 患者通过 Vue eHealth 或医院公众号调阅本人报告;
- G005 RIS 通过标准 API(OpenAPI 3.0)或 HL7 FHIR 提供报告数据;
- 实名认证、电子签名、访问审计由前端门户负责。

**集成度评估**:中(G005 RIS 需提供符合 FHIR 的 ImagingStudy / DiagnosticReport 资源)。

### 5.2 集成成本与价值

| 场景 | 实现成本(人月) | 客户价值 | 商业价值 |
|---|---|---|---|
| 场景 1:基线互通 | 0.5 | 高(基础能力) | 中(竞品基本能力) |
| 场景 2:XDS 区域共享 | 3-4 | 中(仅医联体客户) | 中 |
| 场景 3:Vue Motion 跨终端 | 1-2 | 中 | 中-高 |
| 场景 4:AI 回灌 | 4-6 | 中-高 | 高(差异化卖点) |
| 场景 5:患者门户 | 2-3 | 中 | 中 |

> 注:以上人月为粗略估计,实际工时需 v3.0.7+ 启动详细设计后确定。

### 5.3 非集成建议

在以下方向上,**不建议** G005 RIS 与 Carestream Vue 进行集成,而应保持独立:

- Carestream 自有模态设备(DRX-Revolution 等)的私有 DICOM Tag 解析:由 Vue PACS 统一处理,G005 RIS 不介入;
- Carestream 私有 AI 算法训练:属于 PACS 厂商能力边界,G005 RIS 不参与;
- Carestream Vue Cloud 海外节点:不适用于 G005 RIS 的中国客户。

## §6 v3.0.7+ 优先级

基于 §5 的集成场景评估,建议在 v3.0.7+ 路线图中按以下优先级推进:

### 6.1 P0 — 必须(影响产品基础竞争力)

- **场景 1:基线互通**:G005 RIS 与 Vue PACS 的 DICOM/HL7 标准互通需要保证零障碍,这部分工作纳入 v3.0.7 持续测试套件,确保与 Vue PACS 的兼容性持续回归验证。

### 6.2 P1 — 重要(影响大型医院与医联体客户)

- **场景 2:XDS 区域共享**:在 v3.0.8 启动 XDS-I.b 适配器开发,目标在 v3.0.9 完成 IHE Connectathon 兼容性认证。
- **FHIR ImagingStudy / DiagnosticReport 资源输出**:在 v3.0.8 提供基于 FHIR R4 的报告/影像资源输出,服务于患者门户与跨院调阅。

### 6.3 P2 — 一般(影响差异化竞争力)

- **场景 3:Vue Motion 跨终端报告调阅**:在 v3.0.7+ 后期或 v3.0.8 启动 DICOMweb 端点实现。
- **场景 5:患者门户报告共享**:在 v3.0.8 或 v3.0.9 完成,具体取决于客户需求强度。

### 6.4 P3 — 可选(探索性)

- **场景 4:AI 推理结果回灌**:在 G005 RIS 报告模型支持结构化字段稳定后(预计 v3.0.9 之后)启动。
- **HL7 FHIR 工作流编排(Subscription / Task 资源)**:作为 v4.0 长期演进方向。

### 6.5 路线图时间线(建议)

| 版本 | 周期 | 主要工作 |
|---|---|---|
| v3.0.7 | 2026 H2 | 持续维护,补齐 IHE SWF/PIR 兼容性测试 |
| v3.0.8 | 2027 H1 | XDS-I.b 适配器、FHIR R4 资源输出、DICOMweb 端点 |
| v3.0.9 | 2027 H2 | IHE Connectathon 认证、患者门户 API、IHE ATNA 审计日志 |
| v4.0 | 2028+ | FHIR 工作流编排、AI 回灌、云原生部署 |

> 以上时间线为建议性,**不在本文档承诺范围内**,实际节奏需根据市场需求、资源投入、客户反馈调整。

## §7 工作量

### 7.1 工作量估算原则

- 工作量单位为人月(PM, Person-Month),1 PM ≈ 22 工作日 ≈ 176 工时;
- 估算依据:同类产品集成经验、IHE 标准实施经验、G005 RIS 既有代码模块的复用程度;
- 估算粒度:仅估算"新增开发"工作量,不含"既有维护"、"测试环境搭建"、"客户部署"。

### 7.2 各场景工作量估算

| 场景 | 工作量(PM) | 涉及模块 | 风险等级 |
|---|---|---|---|
| 场景 1:基线互通 | 0.5 | DICOM 引擎、HL7 引擎、报告同步 | 低 |
| 场景 2:XDS-I.b | 3.5 | IHE 引擎、文档库、注册中心适配 | 中-高 |
| 场景 3:Vue Motion 跨终端 | 1.5 | DICOMweb 服务、报告输出转换 | 中 |
| 场景 4:AI 回灌 | 5.0 | 报告模型、字段映射、工作流 | 高 |
| 场景 5:患者门户 | 2.5 | FHIR 资源、OpenAPI 扩展、审计日志 | 中 |
| 测试与认证 | 2.0 | IHE Connectathon、内部回归测试 | 中 |
| 文档与培训 | 1.0 | 接口文档、运维手册、培训材料 | 低 |
| **合计** | **约 16.0 PM** | — | — |

### 7.3 资源需求

- 后端开发工程师(DICOM/HL7/IHE 方向):2 人,约 8 PM;
- 前端 / 报告开发工程师:1 人,约 3 PM;
- 测试工程师(IHE 兼容性测试):1 人,约 3 PM;
- 架构师 / 技术负责人:0.5 人,贯穿全程;
- 产品经理:0.25 人,贯穿全程。

### 7.4 一次性投入与持续投入

- **一次性投入**:16 PM 主要用于 v3.0.7-v3.0.9 三个版本的开发;
- **持续投入**:每年约 0.5-1 PM 用于兼容性维护、Carestream 版本升级适配、客户环境支持。

## §8 风险

### 8.1 技术风险

| 风险 | 等级 | 说明 | 缓解措施 |
|---|---|---|---|
| IHE 标准实现复杂度 | 高 | XDS-I.b 涉及多角色协作,Registry/Repository/CMA 关系复杂 | 优先与现有 IHE 经验丰富的团队合作;考虑引入开源参考实现(如 OpenXDS) |
| DICOMweb 性能 | 中 | 浏览器端大量并发影像调阅对服务端转码能力要求高 | 分阶段引入,先小规模客户验证 |
| AI 回灌的报告模型改造 | 高 | 涉及报告状态机、表单模板、医师审签流程的连锁改动 | 在 v3.0.7 启动 POC,小范围验证后再全面推广 |
| Carestream 私有协议不公开 | 中 | 私有 API 可能在不同 Vue 版本间不兼容 | 优先使用标准协议(DICOM、HL7、FHIR),不依赖私有 API |

### 8.2 合规风险

| 风险 | 等级 | 说明 | 缓解措施 |
|---|---|---|---|
| Carestream Vue 中国 NMPA 注册状态 | 中 | Vue PACS 在中国作为 III 类医疗器械需要 NMPA 注册证,不同模块注册情况不同 | 与锐珂医疗确认每个模块的注册证号,在合规清单中标注 |
| 数据跨境传输 | 中 | Vue Cloud 在中国境外部署可能导致患者数据出境,违反《数据安全法》《个人信息保护法》 | 明确 G005 RIS 客户必须使用 Carestream 中国本地化版本 |
| 患者影像直传的个人信息保护 | 中 | 患者门户涉及个人信息,需符合 PIPL 要求 | 第三方门户负责实名认证与访问审计,G005 RIS 仅提供 API |
| AI 辅助诊断的合规性 | 高 | AI 推理结果在报告中的呈现方式需要符合卫健委相关规定 | 在 AI 报告字段明确标注"AI 辅助诊断,仅供医师参考",不作为最终诊断依据 |

### 8.3 商业风险

| 风险 | 等级 | 说明 | 缓解措施 |
|---|---|---|---|
| Carestream 市场策略变化 | 中 | Carestream 在 2020 年代经历多次业务剥离与重组,Vue 产品线战略可能调整 | 与锐珂医疗保持密切沟通,关注 Carestream 全球公告 |
| 国内 PACS 厂商价格战 | 中 | 国内 PACS 厂商(锐珂本土、飞图、巨鲨等)价格竞争激烈 | G005 RIS 保持"轻量级 RIS"定位,不与 PACS 厂商直接竞争 |
| 集成投入产出比 | 中 | 16 PM 的投入是否能在商业上获得回报? | 仅在出现具体客户需求时启动,避免"为集成而集成" |
| 客户锁定风险 | 中 | 与单一 PACS 厂商深度集成可能导致客户锁定 | 坚持使用国际/国内标准协议,避免私有耦合 |

### 8.4 项目风险

| 风险 | 等级 | 说明 | 缓解措施 |
|---|---|---|---|
| 资源优先级冲突 | 中 | G005 RIS 同时推进其他 v3.0.7+ 任务,集成任务可能被挤占 | 在 v3.0.7 路线图评审时明确优先级 |
| 人员流动 | 中 | IHE 方向专家稀缺,人员离职可能导致项目延期 | 知识沉淀到文档,关键模块双人备份 |
| 测试环境不完善 | 中 | IHE Connectathon 测试需要专用环境,搭建成本高 | 考虑使用 IHE 官方提供的 Gazelle 测试工具 |
