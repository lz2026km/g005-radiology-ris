### 2.3 数据流分类(2026 现状)

| 类型 | 存储 | 写入方 | 读取方 | 适用 |
|------|------|--------|--------|------|
| **静态** | `.ts` 常量 | 编译期 | 任意 | UI 静态文案、状态枚举 |
| **localStorage** | `simulationStore.ts` 封装 | 用户操作 | 任意 hook | 偏好、主题、最近列表 |
| **IndexedDB (Dexie)** | Dexie 4 | 服务层 | `useLiveQuery` | 大列表、离线缓存、报告草稿 |
| **Yjs CRDT** | Yjs Doc | 任意客户端 | `useCollaborativeReport` | 协同报告、Awareness |
| **y-webrtc** | (无服务端中转) | 客户端 P2P | 同上 | 2-5 人小团队 |

### 2.4 性能策略

| 策略 | 实施位置 | 收益 |
|------|----------|------|
| **路由级懒加载** | `App.tsx` 89 个 `lazy()` | 首屏 < 200KB |
| **虚拟列表** | `components/VirtualList.tsx` | 万级数据滚动 |
| **Comlink Web Worker** | `services/*` 重计算 | 不阻塞主线程 |
| **Recharts 按需** | 仅引入图表类型 | 减少打包 |
| **Dexie 索引** | `useLiveQuery` 响应式 | 自动重渲染 |
| **Memo + Callback** | 重点页 useMemo | 重渲染控制 |
| **Storybook 隔离** | `.storybook/` | 组件调试 |

### 3.2 ⭐ v2.1.0 过渡态说明

> v2.1.0 仍为纯前端阶段,采用以下**过渡方案**替代完整后端。

| 维度 | 完整后端 | v2.1.0 替代 | 适用边界 |
|------|----------|-------------|----------|
| 主数据库 | PostgreSQL 15 | **Dexie 4**(IndexedDB) | 单浏览器 / 单设备 |
| 实时通信 | WebSocket 服务端 | **Yjs + y-webrtc** P2P | 2-5 人 / 同子网或 STUN 可达 |
| 缓存/会话 | Redis 7 | localStorage(`simulationStore`) | 偏好 / 主题 |
| API 服务 | Express/NestJS | **MSW 2.6**(浏览器拦截) | dev / demo |
| 认证 | JWT + 服务端校验 | `useAuth.ts` 本地 | 单人本地 |
| DICOM | Orthanc + WADO-RS | cornerstone 加载本地 / 模拟样本 | 演示 / 测试 |
| 文件存储 | MinIO/S3 | IndexedDB Blob | < 50MB 文件 |
| 定时任务 | Bull / cron | 浏览器定时器 | 仅前端任务 |

**为什么可以这样过渡**:
- RIS 的核心交互(报告书写、影像查看、术语查询)都是**单人 / 小团队**密集型
- Yjs CRDT 保证离线编辑后的合并语义,等同于服务端版本控制
- Dexie 支持复杂查询索引,完全覆盖报告列表 / 工作列表场景
- MSW 让前端代码与 OpenAPI 完全解耦,后端就绪后只需切换 baseURL

**何时必须上后端**:
- ⚠️ **> 5 人同时协同**:y-webrtc 性能与稳定性下降
- ⚠️ **多端同步**:医生在 PC + iPad + 手机之间切换
- ⚠️ **真实 PACS 集成**:需 WADO-RS + DICOM 持久化
- ⚠️ **数据合规**:医疗数据需审计、备份、容灾
- ⚠️ **生产部署**:监管要求不可使用 P2P 存储

### 4.4 ⭐ v2.1.0 新增:Dexie Schema(IndexedDB 设计)

```typescript
// 示意:实际 Dexie Schema 在 v2.2.0 引入
// 计划 7 个 Object Store
db.version(1).stores({
  exams:        'id, patientId, modality, status, scheduledAt, priority, [status+scheduledAt]',
  reports:      'id, examId, patientId, radiologistId, status, updatedAt, [status+updatedAt]',
  patients:     'id, patientId, name, idCard, phone',
  devices:      'id, deviceCode, modality, status',
  criticalValues: 'id, examId, patientId, status, reportedAt',
  drafts:       'id, reportId, updatedAt',
  audit:        '++seq, timestamp, reportId, action',
});
```

**与 Prisma 区别**:
- IndexedDB **无外键约束**,需应用层保证
- 复合索引 `[a+b]` 支持组合查询
- `++seq` 自增主键(用于 audit 链)

### 4.5 13 个模型的报告状态机对照

> Prisma 定义 6 态(ReportStatus);前端实际使用 **14 态** 报告生命周期。

| 业务环节 | 前端 14 态(REPORT_STATUS_ORDER) | Prisma 6 态(ReportStatus) |
|----------|--------------------------------|---------------------------|
| draft | 待分配 / 已分配 / 书写中 | DRAFT |
| review | 已提交 / 初审中 / 初审通过 / 终审中 / 已审核 | SUBMITTED / REVIEWED |
| sign | 签发中 / 已签发 | (DRAFT→REVIEWED) |
| published | 已发布 | FINAL |
| special | 修订中 / 已修订 / 已撤回 / 已驳回 / 已归档 | AMENDED / CANCELLED |

**映射策略**:后端迁移时,Prisma ReportStatus 需扩展为 14 态(可作为 v2.2.0 数据库变更的一部分)。
