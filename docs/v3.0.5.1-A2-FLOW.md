## 0. 执行摘要

| 级别 | 数量 | 影响 |
|---|---|---|
| **CRITICAL** | **9** | 鉴权绕过、状态机失守、审计痕迹丢失、职责分离失效 |
| **MAJOR** | **11** | 工作流断链、状态不一致、跨角色越权 |
| **MINOR** | **7** | 边界情况、UX 缺陷、测试覆盖不足 |
| **INFO** | **3** | 设计建议、文档待补 |

**关键结论:**
1. `useAuth()` 与 `utils/auth.ts` 是两套并行的认证通道(后者是 0 注释路径),互不感知,Token 机制几乎形同虚设。
2. `AppLayout.tsx` 与 `ReportReviewPage.tsx` 各自硬编码了"当前用户"(`管理员` / `D005`)。即使 RBAC 路由表已设置 5 个角色,所有真实用户登录后看到的侧边栏与审核员身份仍是 管理员 / 副主任。
3. `reportMachine` / `examMachine` / `orderMachine` / `criticalValueMachine` **没有任何** 守卫能阻止 `actorId === ownerId`(自审自批自签自发布)。
4. `criticalStore.ts:75-95` 在加载历史数据时,会用空字符串重建危急值 actor(`doctorId: ''`),把"我"变成"系统",直接摧毁审计链路。
5. `LoginPage` 完全不验证凭据,接受任意 `username/password`,由前端写入 `localStorage` 冒充登录 — 在开启 Service Worker 缓存的部署中,该值同样会被持久化,等同于客户端可改的 token。

## 1. 鉴权与认证流(CRITICAL)

### CRIT-AUTH-01  任意用户凭据即可登录(无服务端校验)
- **File:** `src/pages/LoginPage.tsx:29-53`
- **描述:**
  `handleLogin` 只检查了 `username/password` 是否非空,然后**直接**根据 `<select>` 选中的角色构造 `payload` 写入 `localStorage["ris_current_user"]`,再用 `window.location.assign(from)` 跳转。整段代码没有任何 `fetch("/api/v1/auth/login")`。
  - `LoginPage.tsx:31-34`:`if (!username.trim() || !password.trim()) { setError(...); return }` 之后没有任何凭据校验
  - `LoginPage.tsx:35-44`:`const matched = DEMO_USERS.find((d) => d.role === selectedRole) ?? DEMO_USERS[0]!;` 直接根据角色 ID 造用户
  - `LoginPage.tsx:46`:`localStorage.setItem("ris_current_user", JSON.stringify(payload))` 客户端写"登录态"
  - `LoginPage.tsx:99-101` 注释也明说"演示账号:任意用户名 + 任意密码即可登录"

  生产构建(`.env.production`)中如果未删除这段 Demo 路径,或被混入 PRD 包,任何攻击者打开 DevTools 即可在浏览器注入 `localStorage` 完成"管理员"登录,绕过整个 RBAC 路由表。
- **建议修复:**
  1. 删除 `LoginPage` 全部 `DEMO_USERS` 与 `localStorage` 写入逻辑,改为 `await api.post("/auth/login", LoginInputSchema.parse(form))`。
  2. 服务端以 `Set-Cookie: HttpOnly; Secure; SameSite=Strict` 下发 refresh token,access token 沿用 `utils/auth.ts` 内存方案(已存在)。
  3. 在 `useAuth()` 中统一从 `getCurrentUser()` 读取,移除 `loadCurrentUser()` 客户端伪造通道(见 CRIT-AUTH-02)。
  4. `.env.production` 增加 `VITE_DEMO_MODE=false` 守卫,构建时若仍存在 demo 路由则 fail build。

### CRIT-AUTH-02  useAuth() 客户端伪造登录态,与 utils/auth 内存 token 双轨制
- **File:** `src/hooks/useAuth.ts:30-77` & `src/utils/auth.ts:121-156` & `src/components/auth/RequireAuth.tsx:7-9`
- **描述:**
  存在两套互不通信的"当前用户"机制:
  - `useAuth` 通过 `loadCurrentUser()` 直接读 `localStorage["ris_current_user"]`(`useAuth.ts:30-38`),即 CRIT-AUTH-01 写的那份。
  - `utils/auth.ts` 的 `setToken/getToken/login` 走**纯内存**(`auth.ts:15`、`148-156`),刷新即丢,默认 30 分钟超时。
  - `RequireAuth.tsx:7` 用 `useAuth()` 检查 `isAuthenticated`,而 `getToken()` 在 API client(`client.ts:10`)里独立使用 — 登录后,`getToken()` 仍返回 `null`,**所有写接口** 实际不带 token,后端会全部 401。

  这两套机制任意生效一个,都会让另一个失效,形成"看着登录、实际全接口失败"或"接口能调、但页面无权限"两种崩溃态。
- **建议修复:**
  - 统一到 `utils/auth.ts`:在 `login()` 成功后 `setToken(...)`,由 `useAuth()` 通过 `getCurrentUser()`(已存在,`auth.ts:210-217`)暴露 `user/isAuthenticated`。
  - 删除 `useAuth.ts:28-38` 的 `loadCurrentUser()` 与 `AUTH_STORAGE_KEY`,以及 `LoginPage.tsx:46` 的 `localStorage.setItem`。
  - `RequireAuth.tsx` 保持现状,`useAuth` 改成读取 `getCurrentUser()`。

## 2. 状态机层 — 7 个状态机的职责分离缺口

### CRIT-SM-01  reportMachine 自审自签可绕过,缺少 actorId 守卫
- **File:** `src/machines/reportMachine.ts:114, 121, 129, 137, 145, 152, 158, 159, 165, 171, 180, 192, 193, 203, 215, 223`
- **描述:**
  所有转移 action 只记录 `actorId`,**没有任何 `guard` 阻止 `event.actorId === context.radiologistId`**(报告作者不能审批/签发/修订/补充自己)。
  - `submitted -> initialReview`:`START_INITIAL_REVIEW` 把 `event.reviewerId` 写入 `context.reviewerId`,无校验。
  - `initialReview -> finalReview`:`APPROVE_INITIAL` 借 `context.reviewerId` 记录动作,但仍允许同一人继续。
  - `coSignReview -> reviewed`:`COMPLETE_CO_SIGN` (`L137`) 接收 `coSignerId`,不校验是否 == `radiologistId`。
  - `signed -> published`:`PUBLISH` (`L158`) `actorId: context.radiologistId`,即"医生可自己签发自己的报告并发布" — 0 守卫。
  - `signed -> amending`、`published -> amending`、`published -> supplementing` (`L159, L165, L166-173`) `actorId: context.radiologistId`,自修自补无障碍。
  - `rejected -> rectifying` (`L208-217`) `rectificationCount` 计数但 actorId 永远是 `radiologistId`。

  对比 `rbacService.ts:50-52` 已经写了 `if (ctx.action === "approve" && ctx.resource.ownerId === ctx.user.userId) return false;`,**但状态机与 RBAC 是分离的两条路径**,前端 UI 调用 `actor.send(...)` 不经过 `protectedRequest`。
- **建议修复:**
  在 `reportMachine.ts:230-235` 的 `guards` 中加入:
  ```ts
  notSelf: ({ context, event }) => {
    const actorId =
      (event as any).actorId ?? (event as any).reviewerId ?? (event as any).coSignerId;
    return !!actorId && actorId !== context.radiologistId;
  }
  ```
  并在以下转移上添加 `guard: "notSelf"`:
  - `START_INITIAL_REVIEW`、`APPROVE_INITIAL`、`APPROVE_FINAL`、`COMPLETE_CO_SIGN`、`COMPLETE_SIGN`、`PUBLISH`、`START_AMEND`、`COMPLETE_AMEND`、`START_SUPPLEMENT`、`COMPLETE_SUPPLEMENT`。

### CRIT-SM-02  criticalValueMachine 通知失败不会推动状态(超时机制失效)
- **File:** `src/machines/criticalValueMachine.ts:135-139, 167-171`
- **描述:**
  `NOTIFY_FAILED` 在 `found` 与 `notified` 两个状态中**只 increment `notificationAttempts`**,不转移目标状态;也**没有延时器 / after 转移**能在 `notifyTimeoutMinutes=5` (`criticalValueMachine.ts:109`) 后自动升级。
  - 临床上"危急值 5 分钟未通知成功 -> 自动升级"是国家卫健委强制要求,目前完全依赖外部调用方记得发 `ESCALATE`。
  - `criticalValueMachine.ts:189-208` 中 `acknowledged` 状态根本没有 `NOTIFY_FAILED` 处理,失败时直接被吞掉。
  - 同样 `resolving` 状态 (`L211-230`) 没有 `ACKNOWLEDGE_TIMEOUT_MINUTES=10` (`L110`) 的升级。
- **建议修复:**
  1. 在 `found` / `notified` 状态使用 XState `after`:
     ```ts
     found: {
       after: {
         300_000: { target: "escalated", actions: "autoEscalateOnTimeout" }
       },
       on: { NOTIFY: ..., CANCEL: ... }
     }
     ```
  2. `NOTIFY_FAILED` 达到阈值(如 3 次)时,转移到 `escalated` 并在 `actions` 中写入 `escalatedReason: "通知连续失败"`。
  3. `notified -> acknowledged` 同样增加 `after` 10 分钟升级。
  4. 单元测试覆盖 `actor.getSnapshot().after(300_000)` 自动升级路径。

### CRIT-SM-03  criticalStore 重建 actor 时清空 doctorId,审计痕迹丢失
- **File:** `src/store/criticalStore.ts:61-96`
- **描述:**
  ```ts

    const actor = createActor(criticalValueMachine, {
      input: { ..., reportedBy: "", notifiedTo: "", ... }   // L65-74 全空字符串

    actor.start()
    if (value.status === "notified" || ...) actor.send({ type: "NOTIFY", to: "", method: ..., by: "" })
    if (value.status === "acknowledged" || ...) actor.send({ type: "ACKNOWLEDGE", by: "" })
    if (value.status === "resolved") { actor.send({ type: "START_PROCESSING", doctorId: "" }); actor.send({ type: "COMPLETE_PROCESSING", note: "" }) }
    ...
  }
  ```
  重新加载危急值时,所有"已发生"事件(`NOTIFY` / `ACKNOWLEDGE` / `START_PROCESSING` / `COMPLETE_PROCESSING` / `ESCALATE`)的 `to/by/doctorId` 全部填 `""`,导致 `criticalValueMachine.history` 中 `actorId` 永久为 `""`。后续 `actor.getSnapshot().context.history` 写入的审计链等于"系统机器人"自审自闭环。

  2. `buildActorFor` 直接 `createActor` 时把 input 填齐,不再 `actor.send` 推演历史(改用 `restoreState` 或把历史作为 input 一次性注入)。
  3. 删除 `MACHINE_STATE_TO_STORE.cancelled: "resolved"` 映射,store 状态枚举扩展 `"cancelled"`,UI 按真实 status 显示。
  4. 在 `criticalValueMachine.ts:111-114` 初始化时,`history` 已经包含 `reportedAt` 条目,不应在 store 层用 send 重放。

### CRIT-SM-04  reportStore.review() 跳过 API 调用,本地篡改审核结果
- **File:** `src/store/reportStore.ts:42-48`
- **描述:**
  ```ts
  review: async (id, type, _doctorId, _doctorName, suggestion, _score) => {
    const field = type === "initial" ? "initialAuditSuggestion" : "finalAuditSuggestion"
    const nextStatus = type === "initial" ? "初审通过" : "已审核"
    set((s) => ({
      reports: s.reports.map((r) => (r.id === id ? { ...r, status: nextStatus, [field]: suggestion } : r)),
    }))
  },
  ```
  整个方法**没有调用** `reportApi.review` 之类的服务端接口,直接 `set(...)` 修改 store 状态。把 `_doctorId` / `_doctorName` / `_score` 都用下划线丢弃,审核人身份未写入 store,前端可以伪装"任意人通过审核"。

  对比 `submit / sign / publish / reject / revise` 全部有 `await reportApi.xxx`,唯独 `review` 是旁路。配合 CRIT-SM-01(状态机无 actorId 守卫),整个审核链可以从客户端伪造。
- **建议修复:**
  1. 改为 `const res = await reportApi.review(id, { type, doctorId, doctorName, suggestion, score });` 与 `submit/sign` 同款。
  2. `reportApi` 增加 `review(id, payload)` 方法(目前 `reportApi.ts:52-56` 只有 `review: (id) => api.post(...)`,无 payload)。
  3. 在 `set` 之前检查 `res.success`,失败时不修改本地状态(与其它方法一致)。

### MAJOR-RPT-01  coSignReview 双签形同虚设:不强制要求与初审/终审人不同
- **File:** `src/machines/reportMachine.ts:135-141`
- **描述:**
  `coSignReview` 接受任意 `coSignerId`,没要求:
  1. `coSignerId !== radiologistId`(自双签)
  2. `coSignerId !== context.reviewerId`(同一审核员既初审又双签)
  3. `coSignerId` 角色必须为主任 / 副主任(目前 `event.coSignerId: string` 无角色概念)
  加上 `reviewerId` 在 `initialReview` 转移中可被 `START_INITIAL_REVIEW` 后再次覆写(`L114`),整条审计链可被反复覆盖。
- **建议修复:**
  - 增加守卫 `coSignerIsDistinct: ({ context, event }) => event.coSignerId && event.coSignerId !== context.radiologistId && event.coSignerId !== context.reviewerId`。
  - coSignerId 改成 `{ userId, role }` 复合类型,在 `coSignReview` 上验证 `role in ["director", "chief"]`。
  - `START_INITIAL_REVIEW` 转移增加 `guard: "reviewerNotAuthor"`,避免 reviewerId 被覆写绕过。

### MAJOR-RPT-02  signed 之后可以 ARCHIVE 直接跳到终态,绕过 published 阶段
- **File:** `src/machines/reportMachine.ts:160-162`
- **描述:**
  ```ts
  signed: {
    on: {
      PUBLISH: { ... },
      START_AMEND: { ... },
      ARCHIVE: { target: "archived" },        // <- 异常路径
    },
  },
  ```
  `signed` 但未发布时,可直接 `ARCHIVE`,导致"已签发但从未发布"的报告被丢弃 — 不符合"先发布才能归档"的医疗记录留存要求(NHC 4-7-1 条款)。
  - 对比 `reported -> published` 必须先 `PUBLISH` 才能 `ARCHIVE`(`examMachine.ts:117`)。
  - 同样 `reviewed`、`coSignReview`、`amending`、`amended` 都允许 `ARCHIVE`,可能把"未发布的已审核报告"直接归档,患者在患者门户看不到,临床医生误以为已发布。
- **建议修复:**
  - 删除 `signed.ARCHIVE`、`reviewed.ARCHIVE`、`amending.ARCHIVE`、`amended.ARCHIVE` 转移。
  - 保留 `published.ARCHIVE` 与 `amended.ARCHIVE`(amended 后已经回到 published 流程,需重新 publish),但需 `guard: "qualityScoreSufficient"`。
  - 增加 `rejected.ARCHIVE` 守卫 `rectifyAttemptsExhausted`,rectifyCount 达到上限才允许归档。

### MAJOR-RPT-03  supplementing 完成后没有"再发布"前的必走流程
- **File:** `src/machines/reportMachine.ts:196-205`
- **描述:**
  `supplementing -> supplemented`(`L196-200`)后,`supplemented -> published`(`L201-204`)仅要求 `qualityScore >= 60`,**没有强制要求重新走 三级审核(初+终+双签)**。
  - 临床含义:报告补充了新内容(可能是新发现病灶),居然不需要再次审核,可直接 PUBLISH — 严重违反《医疗质量管理办法》第三十条"补充诊断需经主治医师以上审核"。

- **建议修复:**

  supplemented: {
    on: {

      PUBLISH: { target: "published", guard: "qualityScoreSufficient AND hasBeenReReviewed" },
    }
  }
  ```
  或者在 `PUBLISH` 守卫中加 `reReviewedAfterSupplement: ({ context }) => context.reReviewedAfterSupplement === true`,该标志由"再审核"事件置位。

- **File:** `src/machines/reportMachine.ts:208-219`
- **描述:**

    on: {
      RESTART: {
        target: "rectifying",
        guard: "rectifyAttemptsBelowMax",
        actions: assign({
          rejectReason: null,                    // <- 原始驳回原因被清掉
          rectifyingReason: null,
          rectificationCount: ...
        })
      }
    }

  ```
  `RESTART` 把 `rejectReason` 设为 `null`,但 `rejectReason` 是临床质量改进与申诉的核心证据。整改完成后审计追溯不到"为什么被驳回"。

  - `COMPLETE_RECTIFY -> writing`(`L192`)让作者直接修改,再 `SUBMIT -> submitted`,等于"重置状态",审计链被截断。
- **建议修复:**
  1. `RESTART` 转移不清 `rejectReason`,改为写入 `rejectedAt`、`rejectedBy`。
  2. `COMPLETE_RECTIFY` 转移到 `submitted` 重新走初/终/双签,而非 `writing` 直写。
  3. `rectifyAttemptsBelowMax` 计数到达上限后,**禁止 RESTART**,只允许 `ARCHIVE` 并记录 `rectificationCount === 3`。
